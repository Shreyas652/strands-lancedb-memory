# Installed API notes (Phase 0)

These notes describe the installed `strands-agents==1.65.0` and `lancedb==0.41.0` wheels in this repository's uv environment, on Python 3.13/Windows. Run `uv run python experiments/api_inventory.py` to regenerate the signature table below and `results/phase0_api_inventory.json`. Source paths in the table are relative to `.venv/Lib/site-packages/`; the line is the declaration inspected by `inspect.getsourcelines`. The table is a candidate API inventory for the design, not a claim that the future store uses all 46 APIs.

## Contract and routing confirmed in source

- `strands/memory/types.py:263-354` defines `MemoryStore`: five attributes (`name`, `description`, `max_search_results`, `writable`, `extraction`), required async `search(query, options)`, and optional async `add`, async `add_messages`, async `initialize`, and sync `get_tools`. `_has_method` ignores inherited Protocol default methods. `MemoryEntry` has `content`, `store_name`, `metadata`. `AddMessagesContext` has only `sequence_numbers`; it has **no run ID** or idempotency key.
- `strands/memory/memory_manager.py:129-181` rejects writable stores without a sink and routes the add tool only to stores with `add`. `:296-346` forwards only `max_search_results` to each store, catches each store's search exception, logs it, and continues with other stores; a single failing store can therefore produce an empty manager result. Backend-specific `SearchOptions` fields are not forwarded through `MemoryManager.search`. `:475-584` defines the actual `search_memory(query, max_search_results=None, stores=None)` and `add_memory(entries: list[str], stores=None)` tools. Default search tool limit is 3; default injection limit is 5 (`:57`, `:667`).
- `strands/memory/extraction/resolve_extraction_config.py:50-112`: `add` only selects `ModelExtractor` by default; the presence of `add_messages` selects raw-message delivery by default even when `add` also exists. This is a semantic consequence of implementing an optional method, not an independent toggle.
- `strands/memory/extraction/coordinator.py:270-312`: extracted facts are written through `add` concurrently; a failed batch may be retried, so writes are at least once. With no extractor it passes filtered messages to `add_messages` with aligned sequence numbers. The filter copies role/content/metadata but drops `tracking_id` (`:314-332`). Sequence numbers advance within an Agent's coordinator but a fresh Agent starts a new sequence; they cannot uniquely identify a durable conversation alone.
- `strands/memory/memory_manager.py:628-701` and `strands/injection/_message_injection.py:80-94,141-185`: injection searches before the model call and appends a temporary `<memory>` block to the last user message. It is not persisted as a conversation turn.
- `strands/vended_memory_stores/file_memory_store/store.py`, `test_memory_store/store.py`, and `bedrock_knowledge_base/store.py` were read as comparison implementations. File/Test search uses token overlap, not semantic vectors. TestMemoryStore deduplicates identical content, which would collapse separate raw messages such as two `ok` turns.
- For a synchronous `Agent` invocation, `Agent.__call__` flushes the attached `memory_manager` after its run. The Phase 0 script uses `memory_manager=manager`; merely passing `plugins=[manager]` does not provide that same flush path in the inspected Agent code.

## LanceDB details checked

- `lancedb.connect(uri)` returns `DBConnection`; `create_table`, `open_table`, `list_tables` and `Table.search` are installed. `Table.create_index(column, config=FTS())` and `Table.create_fts_index(...)` both exist; the latter is marked experimental in its installed docstring. We should choose one path and test index lifecycle rather than assume every search mode works without an index.
- `Table.merge_insert(on).when_matched_update_all().when_not_matched_insert_all().execute(data)` exists and was exercised in `experiments/lancedb_api_smoke.py`. The same smoke exercised hybrid `.vector(...).text(...).where(col("tenant") == "alice", prefilter=True).rerank(RRFReranker()).limit(5).to_list()` and a reopen. Output: `results/phase0_lancedb_api.json`. This is an API smoke, not proof of safe concurrent upserts or tenant isolation against adversarial IDs.
- `lancedb.connect` exposes `read_consistency_interval`; its default is `None`. Cross-process visibility and write serialization need explicit experiments. `Table.optimize` is available, but aggressive version cleanup can interfere with other readers, so maintenance policy needs testing.
- The `connect` signature accepts a string URI, but this does not verify S3 behavior. No S3 emulator or live S3 write/read has yet been run. S3 is not a verified storage target at this phase.

## Absent or changed from the proposed design

`AddMessagesContext.run_id` does **not** exist. A key made only from `(run_id, sequence_number)` cannot be implemented from Strands' callback arguments without the caller supplying a stable run ID separately. `add_memory` takes `entries`, not a `content` argument. Both findings change the public API and idempotency design and are made explicit in `docs/DESIGN.md`.
